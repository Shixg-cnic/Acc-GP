## 1. Jet默认粗化：按源码完整执行一遍

本节只展开Jet的默认粗化，不与我们的算法交替讲。按照调用顺序读：**外层何时开始／结束 → 每层如何选择候选 → 三阶段匹配如何改数组 → 怎样重试 → 剩余点怎样处理 → 映射编号 → 粗CSR怎样构造。**

### 1.1 先确定实际调用的是哪条路径

生产入口 `partitioner::partition` 中：

```text
config.coarsening_alg == 0
    → coarsener的heuristic = MtMetis
    → generate_coarse_graphs
    → 每层generate_coarse_mapping
    → coarsen_match(g, uniform_weights, rand_pool, match_choice=1)
    → build_coarse_graph
```

这里的 `MtMetis` 是Jet内部一个粗化选项名：它执行Jet自己的GPU匹配代码，不是每层调用CPU Mt-METIS。`HECv1/HECv2/HECv3` 是其他分支，不属于这里的默认路径。

源码：[partitioner.hpp](../../sotas/Jet-Partitioner/src/partitioner.hpp) 第75–95行；[contract.hpp](../../sotas/Jet-Partitioner/src/contract.hpp) 第448–491行。

### 1.2 最外层：什么时候继续生成下一张粗图

`partitioner.hpp`先按k覆盖coarsener对象的默认阈值：

```text
cutoff = 8*k
if cutoff > 1024:
    cutoff = max(1024, 2*k)
min_allowed_vtx = cutoff/4
```

因此k=4/8/16/32/64/128时，cutoff分别为32/64/128/256/512/1024。不能把class成员初始化的1000当成生产入口的最终阈值。

`generate_coarse_graphs`保存一张图、该层点重、连接前一层的映射。原图是第1层，然后：

```text
while 当前点数 > cutoff:
    用coarsen_match产生本层map和粗点数nc
    if nc < min_allowed_vtx:
        停止，保留当前图，不使用本次map继续建图
    按map构造粗CSR和粗点重
    将新层加入levels
    if levels.size() > 200:
        停止
```

`levels.size()`包含原图；源码在加入新层后检查。默认这段没有“收缩比例大于0.9就停止”的规则，收缩比例仅出现在DEBUG输出。

随机池在外层以 `std::time(nullptr)` 初始化；CSR构造的hash工作区按原图边记录数预留，后续层使用子区间。初始层的 `uniform_weights` 来自输入；每张新建粗图直接设置为false，随后按加权路径选候选，不重新判定所有边是否恰好相等。

源码：[contract.hpp](../../sotas/Jet-Partitioner/src/contract.hpp) `generate_coarse_graphs`，第494–532行。

### 1.3 单层输入、数组，以及三种状态

当前图为无向对称CSR：`row_map`表示每点邻接起止位置，`entries`存邻点，`values`存边权。当前点可以是上一层产生的粗点。

`coarsen_match`主要维护：

| 变量 | 一开始 | 执行过程中表示什么 |
| --- | --- | --- |
| `hn[u]` | `ORD_MAX` | u当前希望与谁配对；不是已经配成的搭档 |
| `vcmap[u]` | `ORD_MAX` | u的未匹配／临时角色／已匹配根状态，最后改成连续粗点编号 |
| `vperm` | 第一轮用隐式0…N−1 | 仍未匹配且还存在候选的顶点列表 |
| `perm_length` | N | 当前待处理列表长度 |
| `vperm_scratch`, `perm_scratch` | N项缓冲 | 压缩和复制列表，避免读取列表时又覆盖它 |

为方便阅读，后文把两个哨兵记作：

```text
U = ORD_MAX       未匹配，且没有被临时设成接收角色
R = ORD_MAX - 1   本子轮的临时接收角色
0…N-1            已匹配，值为该点对较小的原顶点ID
```

`vcmap`不是从一开始就装最终粗点编号：它先承担并发匹配状态，最后才重新编号。

**默认匹配函数没有收到顶点重量数组，也不检查两点合计重量是否超过某个簇容量。** 点重在建粗图时求和，并供后续初始化／细化使用。不要把我们自己的容量准入规则代入Jet这条函数。

### 1.4 第一次怎样生成hn

有两种情况。

**输入标记为等边权层：** 每个非孤立点从自己的CSR行随机抽一个邻接位置，令 `hn[u]=entries[random_position]`。零度点保持U。

**非等边权层：** 遍历u的邻接，找到最大边权；相同最大边权，用随机数r和邻点ID生成的 `xorshiftHash(v+r)` 决定选择，优先较大的hash值。输出一个邻点ID。

GPU上平均度 `M/N>32` 时，非等权候选查询使用team协作处理一行：先归约最大边权，再归约平局优先级；否则一线程遍历一行。首次等权随机抽邻接的步骤不必扫描完整行。

至此只填好了hn；vcmap仍全部为U。源码：[heuristics.hpp](../../sotas/Jet-Partitioner/src/heuristics.hpp) `pickMatch` 第322–425行、初始化第427–458行。

### 1.5 一次外层匹配循环：四个子轮，每个子轮三个阶段

外层条件是 `while (perm_length>0)`。同一次外层循环执行 `r=0,1,2,3` 四个子轮。**四个子轮之间不重选hn，只改变发起／接收角色，尽量用已有候选完成更多匹配。**

#### 阶段A：给未匹配点设置本轮角色

遍历vperm中的u，令v=hn[u]。没有候选或已经匹配的u跳过。对其他u：

```text
r == 0: condition = (u < v)
r > 0 : condition = (hash(u+r) < hash(v+r))

condition为真：vcmap[u]继续保持U，允许发起申请
condition为假：vcmap[u]设为R，作为本轮可被认领的点
```

这里不是简单按编号奇偶分两组。**每个点的角色取决于它与自己当前候选的比较。** v是否为R，由v自己的候选比较决定，而不是u替v指定。

#### 阶段B：发起者原子认领接收者

再遍历列表。只有hn[u]有效且 `vcmap[u]==U` 的点能发起：

```text
v = hn[u]
root = min(u,v)
old = atomic_compare_exchange(vcmap[v], expected=R, desired=root)
if old == R:
    vcmap[u] = root
```

CAS含义是：只有目标仍处于R，才把它原子改为root。成功的u再写自己的root，于是u、v映射相同。

这段**没有**检查 `hn[v]==u`。只要v本轮是接收角色，u认领成功就能与v匹配，即使v本来想找的是另一个点。若多个u争抢同一v，只有一个CAS成功；胜者由实际原子执行顺序决定，不会在这里再比较谁的边更重。

为什么u不会同时被别人抢走？因为u为U，而申请者只能认领状态为R的目标。发起角色和接收角色在这个子轮分开。

#### 阶段C：清除未使用的临时角色

第三个kernel将仍为R的顶点恢复为U；成功匹配的顶点保留root。然后进入下一个子轮，改变比较用的hash，hn保持原样。

所以一次外层循环的四个子轮，对应4次角色设置、4次认领、4次恢复。源码：[heuristics.hpp](../../sotas/Jet-Partitioner/src/heuristics.hpp) 第462–500行。

### 1.6 逐数组跟踪：一个不是互选的匹配如何发生

下面直接演示单层 `coarsen_match`，不经过外层停止点数阈值。四个点0、1、2、3，点重都为1，无向边为：

```text
0—2:10    1—2:9    2—3:8    0—3:4
```

一种CSR邻居顺序为：

```text
row_map = [0, 2, 3, 6, 8]
entries = [2,3,  2,  0,1,3,  0,2]
values  = [10,4, 9, 10,9,8,  4,8]
```

选最重边后：

| u | hn[u] | 原因 |
| --- | ---: | --- |
| 0 | 2 | 10大于4 |
| 1 | 2 | 只有2这个邻点 |
| 2 | 0 | 10大于9、8 |
| 3 | 2 | 8大于4 |

初始 `vcmap=[U,U,U,U]`。

**第一个外层循环，r=0：**

| u | 比较u<hn[u] | 角色／阶段A后的vcmap |
| --- | --- | --- |
| 0 | 0<2，真 | U，发起 |
| 1 | 1<2，真 | U，发起 |
| 2 | 2<0，假 | R，接收 |
| 3 | 3<2，假 | R，接收 |

此时 `vcmap=[U,U,R,R]`。0、1都申请2。假设1先CAS成功，这是允许的一种GPU执行顺序：

```text
1成功：vcmap[2]=1，vcmap[1]=1
0失败：目标2已经不是R，vcmap[0]仍为U
3没有收到成功申请，恢复R→U

vcmap = [U,1,1,U]
```

**这次形成的是{1,2}，尽管2的hn是0。** 也就是说，10权重的互选边0–2不保证一定先于9权重的申请1–2获胜。

接着r=1、2、3仍使用旧hn。0、3仍然想找已经匹配的2，所以无法认领它。四个子轮结束后才更新候选：

```text
0的旧目标2已匹配，重新扫描未匹配邻点，只剩3 → hn[0]=3
3的旧目标2已匹配，重新扫描未匹配邻点，只剩0 → hn[3]=0
```

压缩剩余列表得到 `vperm=[0,3]`、`perm_length=2`。

**第二个外层循环，r=0：** 0<3所以0发起；3<0为假所以3接收。0认领3，根为0：

```text
vcmap = [0,1,1,0]
点对 = {0,3}, {1,2}
```

之后剩余列表为空，外层匹配循环结束。这里的每个状态都能对应到前面三个kernel的读写。

### 1.7 四个子轮之后：不是所有剩余点都重新扫描邻接

`pickMatch<false,...>`的入口判断相当于：

```text
如果u已匹配：跳过
如果hn[u]已经无效：跳过
如果旧目标hn[u]仍未匹配：保留旧目标，不重新扫描
否则：旧目标已被占用，重新选择
```

重新选择只考虑 `vcmap[v]==U` 的邻点。加权层选最重边、随机hash打破平局；等权层对可用邻点比较随机hash，而不是再次直接随机抽原CSR位置。若不存在可用邻点，hn[u]设为U。

随后scan压缩满足以下两个条件的点：

```text
vcmap[u] == U     自己尚未匹配
hn[u] != U        仍有一个可申请的邻点
```

scan返回新 `perm_length`，主机决定下一次while。点已匹配，或者已经无可用邻点，都会离开这个列表。

所以循环结束表示**没有还需要继续尝试普通邻边匹配的点**，并不保证每个点都已有搭档。源码：`pickMatch`入口条件，以及第502–532行。

### 1.8 默认路径的三种补充匹配：leaves、twins、relatives

`match_choice=1`启用下面三个阶段。每个阶段前都重新统计全图未匹配比例；只有 `unmatched/N>0.25` 才执行该阶段。它们顺序运行，不是三选一，也不循环到所有点都匹配。

**A．Leaf匹配。** 收集未匹配且当前图度数为1的点。每点用唯一邻点ID作为分组键。同一个邻点的多个叶子在组内两两配对，即使叶子之间没有直接边。例如a、b都只连中心x，可匹配{a,b}；不把x加入这对。

**B．Twin匹配。** 若未匹配比例仍>25%，对所有未匹配点计算与邻接顺序无关的摘要：对每个邻点x计算y=hash(x)，将y²+y累加为64位摘要。摘要相同的点两两匹配。此摘要用邻点ID，不使用边权；源码将摘要相等视作邻接相同，没有再逐项核验整个邻居集合，所以hash碰撞也可能归到同组。

**C．Relative匹配。** 若比例仍>25%，每个未匹配点从邻点中选择“邻点度数最小”的一个；度数相同时选较大边权，仍相同则保留遍历中已有选择。以所选邻点ID作为分组键，同键点两两匹配。所选邻点本身可以已经匹配，因为这里只借它的ID分组，不把它加入新点对。

三种都调用 `matchHash`：

1. 用线性探测找到／认领属于该分组键的hash槽。
2. 槽中另有一个等待顶点ID，初始为−1。
3. 来一个点时，若槽空则用CAS放入自己；若已有另一个点，则用CAS取走它、清空等待槽，并将这两个点的vcmap写成较小ID。
4. 后续同键点重复上述过程。因此4个同键点可产生2对，奇数个时留下1个。

没有在同键组内做全局最优配对，也没有统一合成一个多点大簇。源码：[heuristics.hpp](../../sotas/Jet-Partitioner/src/heuristics.hpp) `matchHash`第278–319行、补充阶段第535–640行。

零度点在twin阶段得到摘要0，在relative阶段保留初始键ORD_MAX。当前 `matchHash` 没有“键等于nullkey就提前跳过”的判断，不能把零度点描述成必然跳过补充阶段；它们也可能经同键槽形成点对。最终singleton步骤处理的是所有补充操作后仍未匹配的点。

### 1.9 最后未配对点与连续粗编号

所有补充阶段结束后，仍 `vcmap[u]==U` 的点置为 `vcmap[u]=u`，作为singleton。至此每个点要么指向本对较小ID，要么指向自己。

然后将离散根ID改成0…nc−1：

1. 对满足 `vcmap[u]==u` 的根做前缀计数，根的vcmap改为连续编号。
2. 非根暂时把原根ID加N保存。这样原根引用与已经产生的连续编号不会混淆。
3. 再遍历非根，令 `vcmap[u]=vcmap[vcmap[u]−N]`，取得其根的连续编号。

前面的四点例子：

```text
原根映射     [0,1,1,0]
编号扫描后   [0,1,5,4]     N=4，非根引用暂加4
传播编号后   [0,1,1,0]
nc = 2
```

现在map才真正表示细点→粗点编号，返回给 `build_coarse_graph`。源码第642–674行。

### 1.10 粗CSR构造：实际使用全局hash，不是排序边列表

输入当前CSR、点重与map。目标粗图应满足：同粗点内部边删除；相同粗点对之间的边权相加；粗点重量为成员重量之和。

**步骤1，统计原始行空间和粗点重量。** 对每个细点u：

```text
c = map[u]
degree_initial[c] += degree(u)
coarse_vertex_weight[c] += vertex_weight[u]
```

均用原子累加。这里空间按所有原始邻接记录计数，包含稍后会删除的内部边及重复粗边，不是最终粗度数。

**步骤2，扫描出各粗行hash区间。** 将上述长度做exclusive scan，得到 `hrow_map`。清空对应 `htable`键与`hvals`权重。每个粗点使用自己的一段hash区间。

**步骤3，映射每条细边并累加。** 对细边u→v，令c=map[u]、d=map[v]：

```text
若c==d，跳过内部边
否则在粗行c的hash区间查找键d：
    初始槽 = abs(xorshiftHash(d)) % 行区间长度
    空槽用CAS认领；不同键则线性探测下一槽，尾部环绕
    找到／建立d的槽后，atomic_add(hvals[slot], edge_weight(u,v))
```

这一步同时完成重复粗边归并。GPU上若 `hash_size/N>=12` 或存在大度行，使用team协作；否则用range方式处理细行。不是任何图都固定一线程处理所有粗图构造工作。

**步骤4，统计实际非空槽。** 对每个粗行统计不同目标键的个数，即真实粗度数；再exclusive scan得到最终CSR offsets和总记录数。

**步骤5，写出CSR。** 为真实输出数量分配邻点和权重数组，将每粗行的非空hash槽复制进去。team版本用共享计数器原子预留行内输出位置，不要求邻居按ID排序。粗点重量已经在步骤1得到。

这些阶段在源码中由kernel、scan、清空与多处fence串接，不是一次kernel内完成所有事情。源码：[contract.hpp](../../sotas/Jet-Partitioner/src/contract.hpp) `countingFunctor`、`combineAndDedupe`、`countUnique`、`consolidateUnique`、`build_coarse_graph`，第152–445行。

### 1.11 用前面的四点例子核对输出

最终map为 `[0,1,1,0]`，所以粗点P={0,3}、Q={1,2}，点重均为2：

- 0–3的4与1–2的9是内部边，删除。
- 0–2的10、3–2的8都连接P和Q，合并为18。
- 对称CSR分别保存P→Q与Q→P，各18，不把一个方向写成36。

```text
coarse_vertex_weight = [2,2]
coarse_row_map       = [0,1,2]
coarse_entries       = [1,0]
coarse_values        = [18,18]
```

构造hash空间时，P成员的原始度数2+2=4，Q成员为1+3=4，总共先准备8个槽；去内部边和重复目标后，最终只输出2条有向记录。这正好说明“原始空间统计”与“最终CSR统计”为何需要两次不同的计数／扫描。

然后把新图、点重和本次map保存到levels，回到第1.2节判断是否继续粗化。

### 1.12 与源码相对应的单层伪代码

```text
JetCoarsenMatch(G, uniform):
    U = ORD_MAX; R = ORD_MAX-1
    hn[:] = U; vcmap[:] = U
    若uniform，随机抽邻接位置生成初始hn
    否则按最重边及随机hash生成初始hn
    pending = 所有顶点

    while pending非空:
        for r in [0,1,2,3]:
            # 三个独立的并行阶段
            for u in pending并行:
                若hn[u]无效或vcmap[u]!=U，跳过
                condition = r==0 ? u<hn[u] : hash(u+r)<hash(hn[u]+r)
                若condition为假，vcmap[u]=R

            for u in pending并行:
                若hn[u]无效或vcmap[u]!=U，跳过
                v=hn[u]; root=min(u,v)
                若CAS(vcmap[v],R,root)成功，vcmap[u]=root

            for u in pending并行:
                若vcmap[u]==R，恢复为U

        for u in pending并行:
            若u已匹配或hn[u]无效，跳过
            若旧目标hn[u]仍未匹配，保留hn[u]
            否则，从未匹配邻点中重选，找不到则hn[u]=U
        pending = 压缩出vcmap[u]==U且hn[u]!=U的点

    若未匹配比例>25%，做leaf同键两两匹配
    重新统计；若比例>25%，做twin摘要两两匹配
    重新统计；若比例>25%，做relative同键两两匹配
    剩余点各自成singleton
    根前缀编号，传播给非根
    return map, nc
```

`build_coarse_graph`接着按第1.10节处理，不在该匹配循环内部重建CSR。对当前默认路径，完整的单层粗化就是“以上map生成＋hash构造粗图”。

### 1.13 读懂以后再定位执行开销

现在每项开销都能对应具体步骤：四个子轮有12个角色／提交kernel；旧目标被占用时才重复扫描邻接；压缩pending返回数量控制外层循环；未匹配比例高时追加三种hash配对；粗CSR再经历原始计数、hash空间扫描、hash插入、真实度数计数、最终扫描和写出。

其中哪些操作占主要时间取决于图结构和实际轮次；这些是已经核对的操作来源，不代表所有图都由同一个步骤主导。第3节比较这些操作与我们实现的对应差异，第7节再完整讲我们的粗化规则。

## 3. 粗化：算法流程、执行瓶颈与我们的改进

### 3.1 要解决的挑战

现有粗化方法中的匹配竞争和合并依赖，使GPU需要经过多轮协调才能确定聚合结果。重复邻接搜索、组标识传播和逐渐缩小的活动集合增加了执行开销。与此同时，扩大并行聚合规模又需要合理分配有限簇容量，以保留图中的强连接结构。

我们让接收簇在一轮内保持不动，允许多个单点直接加入，使每个被接受顶点的归属在本轮直接确定。容量不足时，按首选相对次选的连接优势排列请求，通过重量前缀批量确定接受集合。配合有界的增长轮次，这一组织减少了合并依赖和残余重试，同时保留对强连接的选择。

这段挑战有明确的对象：**Jet对应匹配重试、条件触发的邻居重选和剩余集合维护；G-kway对应合并关系上的组标识传播与收敛判断。** 两者都能并行执行一轮内的工作，但下一轮需要使用上一轮结果。这里的“多轮协调”指轮次之间的依赖，并不是把整个算法说成串行算法。

### 3.2 三列对照：一层粗化如何从输入走到输出

**共同输入：** 当前层的图、顶点重量和边权；此处一个“顶点”可能已经代表上一层合并的多个原始顶点。**共同输出：** 当前顶点到粗点的映射、粗点重量，以及合并重复边并去掉内部边后的粗图。

下表每一列独立从上向下读。J、G、A分别是三种方法的步骤编号，后面的瓶颈分析直接引用它们。表中的循环发生在**当前层内部**；完成粗图构造后才进入下一层。

| Jet：默认匹配粗化 | G-kway：合并关系传播 | Acc-GPart：稳定接收簇聚合 |
| --- | --- | --- |
| **J1．选邻居。** 等边权初始层随机选邻居；加权层优先选最重邻边，平局用hash决定。 | **G1．选邻居。** 各点扫描邻接，选最重邻边；边权相同时优先较低度邻居。 | **A1．初始化簇。** 按当前层结构决定是否做一次互选匹配种子；未合并点各自成簇。 |
| **J2．分配临时角色。** 根据点与候选的ID／hash关系，设置本子轮的主动点和临时接收点。 | **G2．初始化组标识。** 每个点先有自己的组标识，保留G1选出的邻居关系。 | **A2．冻结角色。** 仅从单点簇中按hash选择迁移源；多点簇和未选中的单点作为接收簇，本轮不迁出。 |
| **J3．原子认领。** 主动点尝试认领候选；一个接收点最多与一个源配对，竞争失败的点继续等待。 | **G3．传播组标识。** 沿所选邻居关系比较并原子更新组标识，使连接的点逐步归入同组。 | **A3．形成请求。** 仅对活动源聚合到各接收簇的连接；选容量允许的最强目标，并计算首选与次选的连接优势值。 |
| **J4．恢复并重试。** 清除未成功的临时接收标记，再做J2→J3；每个外层循环共四个匹配子轮。 | **G4．判断收敛。** 将“本轮是否变化”传回CPU；有变化就返回G3，再传播一轮。 | **A4．批量分配容量。** 按目标簇分组、连接优势降序排列请求，用完整顶点重量前缀确定接受集合。证明全部可放下时直接全收。 |
| **J5．必要时重选邻居。** 仍未匹配且旧候选已被占用的点，重新扫描邻接寻找未匹配邻居；旧候选仍空闲则复用。 | **G5．限制组大小。** 收敛后按组标识排序，拆分过大的组；本地实现每组最多六个成员。 | **A5．直接提交到接收根。** 接受的源直接加入稳定目标簇；一个簇可以接收多个源，被拒绝的源保持单点。 |
| **J6．整理剩余集合。** 压缩“未匹配且仍有候选”的点，取得数量；非空则返回J2，继续处理剩余点。 | **G6．形成粗点映射。** 统计组并连续编号，按组累加顶点重量。 | **A6．有界继续增长。** 更新簇数，达到收缩条件则停止，否则返回A2；常规增长最多四轮，已合并点不再作为源扫描邻接。 |
| **J7．处理残余点。** 未匹配比例较高时依次尝试叶子、相似邻接、共同邻居等补充配对；最后未匹配点保留为单点。 | **G7．构造粗图。** 搬运映射后的边，分段排序、合并重复边并去掉内部边。 | **A7．处理残余结构。** 按容量打包孤立点；收缩不足时，对共享首选邻居的剩余单点做补充配对。 |
| **J8．构造粗图。** 连续编号、累加点重；通过粗行hash累加跨簇边，生成下一层CSR。 | **本层结束。** 判断是否还需下一层粗化。 | **A8．一次构造粗图。** 连续编号、累加点重并收缩CSR。种子和各增长轮共享当前层CSR及簇映射。 |
| **循环位置：J2→J4，以及J2→J6。** | **循环位置：G3→G4。** | **循环位置：A2→A6，最多四轮。** |

流程依据：Jet [heuristics.hpp](../../sotas/Jet-Partitioner/src/heuristics.hpp) `coarsen_match`及[contract.hpp](../../sotas/Jet-Partitioner/src/contract.hpp)；G-kway [coarsen.hpp](../../sotas/DAC_g-kway/gkway/coarsen.hpp) `coarsening`；Acc-GPart [coarsen.cu](../src/coarsen.cu) `aggregate_typed`、[singleton_growth.cuh](../src/coarsening/singleton_growth.cuh)。

### 3.3 把挑战中的每项开销对应到流程

**① 匹配冲突与多轮协调：J3→J4→J6。** 多个点可能选择同一个接收点，但J3只能让其中一个配对成功。其余点还要经过角色恢复、后续子轮和剩余集合整理，才能继续争取匹配。每个子轮包含角色设置、原子认领、标记恢复三个阶段，四个子轮就是12次kernel启动；外层还需J5和J6。GPU能够并行处理同一阶段的点，但这些阶段必须依次推进。我们的A2先固定角色，A4一次算出容量允许的接受集合，A5让多个源直接并入一个接收簇，把反复配对竞争组织成按接收簇处理的批次。

**② 重复邻接搜索：J5。** 当一个点的旧目标已经被其他点占用，它需要重新检查邻接关系，寻找新的未匹配目标；同一个点可能在不同外层循环再次发生这种情况。首次选邻居、旧候选仍可用的情况，不属于这项重复工作。我们的A3也可能在不同增长轮重新计算未合并源的连接，但成功并入的源退出后续邻接搜索，而且A6为常规增长设置四轮上限。区别是控制残余搜索的范围和轮次，不是完全取消重新计算。

**③ 逐渐缩小的活动集合：J6返回J2。** 随着匹配成功，剩余列表越来越短；如果尾部还需多个外层循环，就会用较少的顶点继续支付角色处理、kernel启动、列表压缩和主机完成判断的成本。这里“并行度不足”具体指每轮可执行的有效任务减少，固定调度成本更难被摊薄。我们的A6根据收缩程度或轮数结束常规增长，再由A7处理特定残余结构。Jet本身也会排除已经匹配的点；我们的差别在于多点接收和有界推进，并不是首次使用活动集合。

**④ 组标识传播：G3→G4。** G1选出的关系可能形成链，例如u→v、v→z；各点完成选邻居后，组标识还需沿这些关系统一。G3反复读取／原子更新组标识，G4每轮传回变化标志，直到不再变化。该循环不重选最重邻居，也不使用Jet那种逐步压缩的待匹配集合；它的成本是组标识传播和收敛控制。我们的A2禁止接收簇本轮迁出，因此A5可以直接写入目标根，不需要为本轮产生的迁移链反复传播归属。

**两种基线的瓶颈不能混写。** “重复邻居重选＋剩余集合尾部”对应Jet；“沿合并关系传播组标识”对应G-kway。G-kway已经支持多点聚合，Jet也已经有临时角色划分。我们的区别是将稳定接收、多点准入和有界残余增长组织在同一套层内流程中。

### 3.4 我们为什么适合GPU：从流程推导执行优势

**稳定接收，减少合并依赖。** A2将源集合与接收根集合分开，每个源只申请接收根，接收根本轮不迁出。因此A5提交时，目标归属已经确定；多个源可以并行写各自的簇编号。这个性质消除了由本轮迁移产生的根查找／传播链。容量扫描、簇重量累加和阶段之间的依赖仍存在。

**批量准入，把容量竞争变成分段任务。** 对接收簇A，将请求按连接优势降序排为v₁,…,vₘ；冻结本轮开始时的簇重量W(A)，容量为C。A4计算：

$$
P_i=\sum_{j=1}^{i}w_{v_j},\qquad
v_i\text{ 被接受}\iff P_i\le C-W(A).
$$

排序后可用分段并行前缀和计算P，再并行判断各请求；不同接收簇拥有独立的容量预算。这样得到明确的接受集合，源点无需在本轮失败后立即重选、再次争抢。这里付出的成本是请求排序与扫描；当容量充分界证明全部请求都能放下时，代码省略次强统计、排序、前缀和旧重量gather，直接提交。充分界及实现见第7.7节。

**有界增长，控制重复工作。** A3的邻接工作覆盖本轮活动源，而不是所有已聚合顶点；A6限制常规增长轮数。若Dₜ是第t轮活动源，dᵥ是当前层顶点度数，该部分扫描的工作量由各轮的Σ(v∈Dₜ)dᵥ决定。多点簇的成员不再成为源，但仍可以作为邻居被读取。角色设置、簇数统计等全点处理，以及排序和补充阶段，需另计。

**连接优势维护有限聚合机会下的选择质量。** 对源v，到候选接收簇A的连接为a(v,A)=Σ(u∈A)ωᵥᵤ；在角色和完整重量容量允许的候选中，取最强与次强连接a₁、a₂：

$$
\Delta a(v)=a_1(v)-a_2(v).
$$

这就是“连接优势值（Affinity Margin）”，与源码的 `regret`、第7节原有记号r(v)含义相同。只有一个可选目标时a₂=0；没有目标则不申请。它把容量优先分配给首选相对备选优势更大的请求。例如等重量的两个源分别有连接(12,11)与(10,2)，后者的连接优势8大于前者的1，获得更高优先级。该指标管理有限容量下的选择；并行执行优势来自A2—A6的整体组织。

**层内增长和粗图层数分开看。** A1—A7共享当前层CSR，A8才构造下一层，避免为种子与增长的中间状态反复建图。Jet、G-kway也在本层映射完成后才建粗图，因此“每层只建一次CSR”不是它们所缺少的功能。多点接收提供了更强的局部聚合能力；我们当前有约一半点数的增长目标，是否最终减少了粗化层数，要看实际层次记录，不能直接照搬G-kway“减少层数”的结论。

可以据此凝聚为一条完整优势：**稳定接收簇聚合通过冻结迁移角色消除同轮合并链，通过多点批量准入与有界增长控制匹配重试和残余搜索，再用连接优势分配有限簇容量。** 这些步骤解释了执行结构为什么适合GPU；实际阶段耗时与端到端加速对应第9节已有结果。当前粗化仍有主机读取簇数，并非整个循环都在设备端运行。

### 3.5 粗 CSR：局部数据复用与全局中间结果

| 实现 | 粗图构造中的主要组织方式 | 对应 GPU 成本 |
| --- | --- | --- |
| Jet | 分配/清空粗行 hash 空间；线性探测、原子累加重复边；计数、前缀、输出 | 不规则全局 hash 访问、竞争和多阶段全局数组读写 |
| G-kway | 搬运映射后的边，ModernGPU segmented sort；单线程逐粗行归并；前缀与输出 | 边记录排序和中间数据搬运；粗行归并工作长度不均 |
| Acc-GPart | 满足短行条件时，warp 内按行排序、分段归并；否则使用全局 radix/reduce | 短行排序及归并中的中间交换在寄存器/shuffle 中完成，减少该步骤对全局中间数组的依赖 |

Acc-GPart 的短行上限是 **512 条原始粗行记录**，按 32/64/128/256/512 分档；长短行分 kernel，避免短行承担 512 项路径的资源配置。scatter、最终 CSR 输出和偏移构造仍需要全局内存。该优化既不是所有层都走，也不是整个 CSR 都在片上存储。

源码：Jet [contract.hpp](../../sotas/Jet-Partitioner/src/contract.hpp) `build_coarse_graph`；G-kway [coarsen.hpp](../../sotas/DAC_g-kway/gkway/coarsen.hpp) `contraction`；Acc-GPart [contraction_rows.cuh](../src/coarsening/contraction_rows.cuh) 与 [coarsen.cu](../src/coarsen.cu) 约第 1480 行。

## 4. 细化：算法流程、执行瓶颈与我们的改进

### 4.1 要解决的挑战

细化的并行执行受移动之间的收益耦合和容量依赖限制：相邻点共同移动会改变各自的收益，一个方向的移动又可能需要另一方向释放容量。逐点过滤和邻接排斥限制了可同时处理的移动；先并行移动再修复负载，则增加修复提案、连接更新和状态维护。重复邻接访问与逐轮主机判断进一步增加了执行成本。

我们将相互释放容量的短移动组合成一次交换，让它们一起决定、整体提交。不同分区对分别处理各自的容量，候选之间的边用精确收益计算处理，允许相邻移动参与同一批。交换搜索设置固定预算；大层常规LP与修复由设备端控制，连接查询和更新复用已有状态。这样分别处理移动之间的依赖，以及执行过程中的重复访问和主机等待。

具体对象分别是：G-kway的单点可行性过滤、独立集合及批量上限；Jet的移动／修复循环与主机控制。Jet已经支持相邻点并行移动，也已经使用连接缓存和增量更新，不能将G-kway的限制套到Jet上。当前Acc-GPart保留LP／afterburner和容量修复；容量互补交换在恢复最佳可行LP状态后、N≤65536的层执行。

### 4.2 三列对照：一层细化如何从输入走到输出

**共同输入：** 当前层图、继承的分区标签、顶点／边权、分区重量及平衡限制。**共同目标：** 降低切边并满足各自的平衡约束，输出更新后的标签、切边和分区重量。本节比较算法操作，不假设三个实现的取整及容量规则完全相同。

每列从上向下读，并按其中的分支／返回说明推进；JR、GR、AR是细化步骤编号。LP指按顶点连接选择移动目标；afterburner指根据邻接候选的优先级校正收益。表中循环在当前层内执行，结束后才将标签投影到更细层。

| Jet：并行LP与负载修复 | G-kway：独立移动集合 | Acc-GPart：设备端LP与容量互补交换 |
| --- | --- | --- |
| **JR1．准备状态。** 继承标签，建立顶点到分区的连接缓存，保存当前／最佳状态。 | **GR1．准备候选信息。** 根据标签确定边界顶点、各点的目标分区和单点收益。 | **AR1．投影并选择细化层。** 最粗层、原图、超载层及达到点数增长条件的层进入细化；其余层只投影标签。 |

### 4.3 把挑战中的每项开销对应到流程

**① 单点容量过滤使互补移动无法进入候选集合：GR2。** G-kway先检查目标当前是否能装下整个顶点，之后才在GR4处理一批请求的净重量。如果两个分区都已满，一个方向必须依赖另一个方向迁出重量才能执行，两个单点就可能在GR2同时被过滤；后面的批前缀无法恢复这些候选。我们的AR7保留单独容量不可行的正收益片段，先按净重量组合，再决定是否提交。这里首先解决的是可执行组合的覆盖；直接过滤也可能让基线更早结束，不能把丢失候选本身说成必然耗时更长。

**② 邻接排斥与固定批量限制有效并行工作：GR2→GR3。** 独立集合过滤让相邻的合格候选不能同时进入本批；排序之后的1024上限又限制了本轮实际参与前缀处理的候选量。候选很多时，前面的生成和排序未必转化成同等规模的实际移动，剩余改进需要后续批次继续处理。我们的AR3沿用允许邻接移动的LP校正；AR7则允许不同交换之间有边连接，通过精确边事件计算联合影响，只禁止两个交换使用同一个顶点。Jet的JR3已经允许相邻移动，区别于Jet的算法点是互补片段的显式组合，而不是首次允许相邻点并行。

**③ 同一邻接行按不同目标重复扫描：GR6。** G-kway先扫描顶点v的邻居以识别目标分区，再对每个相邻目标调用 `calculate_gain`，各扫一遍相同邻接行。若度数为dᵥ、相邻目标数为qᵥ，这部分工作约为O(dᵥ+k+qᵥdᵥ)。它只对受影响点执行，重复发生在这些行内部。我们的AR2建立可复用的分区连接，AR3从连接项选目标，AR4增量更新或重建脏行，减少逐目标重扫原始邻接。Jet也有缓存和增量更新；对Jet的差别要对应我们进一步采用的表示选择、活动范围、融合维护和循环控制。OnDemand路径仍有按需邻接查询，不套用缓存路径的省时结论。

**④ LP移动之后，负载修复需要额外候选与维护：JR4→JR6→JR2的修复分支→JR5→JR4。** Jet没有在每个LP提案前要求目标必然装得下所有并发进入的点；移动之后若超载，就继续产生弱／强修复提案。每批修复也需要执行移动、维护连接和计算cut。我们的AR3—AR6仍保留这一过程，具体减少的是AR5的重复目标查询和原子预约，以及AR6的主机往返。带权层的修复代价反馈在AR3降低预计需要昂贵修复的目标吸引力；是否减少实际修复轮数由运行记录决定。AR7的交换从可行状态出发，最终按完整净重量提交，因此这个交换批次本身不需要先超载再调用修复。

**⑤ 每轮设备结果返回主机后才能决定下一步：JR3、JR4、JR6，以及GR3、GR4、GR5。** Jet的候选压缩读取数量、移动后读取cut和最大负载，主机再决定继续LP还是修复；G-kway读取候选数、前缀结果及cut。这里增加的是设备／主机同步和控制往返，不是所有GPU计算都变成串行。我们的AR6把大层LP、嵌套修复、终止判断及条件检查点放进CUDA条件图，设备状态直接控制后续节点。层间切换、小层和AR7交换仍有主机参与。

**⑥ 相邻细化层重复付出准备与搜索成本：JR8→JR1。** Jet在反粗化的各层调用细化，建立该层连接状态并运行搜索。我们的AR1在分辨率增加不足且容量可行时仅投影，达到点数增长条件后再细化，减少这些层的缓存构建和迭代。它改变了搜索调度和工作量，属于完整算法的一部分；不能将由此节省的时间都归给AR7交换。

**对应关系归纳：** G-kway的主要结构限制是“候选入口过滤＋受限批次＋逐目标重扫”；Jet已经扩大并行移动范围，主要需要进一步处理的是“移动／修复的执行成本、状态维护及主机控制”。我们的容量互补交换处理移动之间的容量与收益耦合，设备端循环和增量执行支撑完整细化速度。

### 4.4 容量互补交换：我们的算法主线怎样处理依赖

AR7中的“交换事务”就是**必须整体选择和提交的一组顶点移动**。它可以同时包含A→B和B→A两个方向。设当前分区重量为L_A、L_B，容量为C，正向集合为S，反向集合为T：

$$
d=w(S)-w(T),\qquad
L_A'=L_A-d,\quad L_B'=L_B+d.
$$

于是严格容量条件为：

$$
L_A-C\le d\le C-L_B.
$$

例如L_A=L_B=C=10，两个方向各移动重量2。单独执行任何一边都会使接收分区变成12；合起来d=0，两边仍为10。我们的任务是生成并评估这个完整交换，不必先执行一边、处理超载后再等待另一边。Jet的并行LP也可能同批实现这样的交换；我们的区别是搜索时显式保留和配对容量互补片段。

具体流程如下，与三列表中的AR7对应：

1. **选互不共享分区的配对。** 根据分区间连接建立商图，匹配A—B、C—D等分区对；一个分区在同批中只参加一个配对。各对的容量状态可以独立处理。
2. **在固定预算内生成片段。** 对配对边界采样种子，用两种优先策略生长；每条轨迹每侧最多4点、合计最多8点。保留一个正收益可行长状态，同时保存成员数1—4对应的正收益短前缀，后者允许暂时单独容量不可行。生长可以经过负收益中间状态。
3. **按净重量查找互补片段。** 规范化并去重相同成员集合，按分区对和净重量排序。对净重dᵢ的片段，二分查找能使dᵢ+dⱼ落入可行区间的候选，最多检查四个代表；成员不重叠、合计不超过8点时，精确计算跨片段边影响，保留正收益组合。
4. **统一筛选顶点冲突。** 可行长状态、可行短片段和互补组合进入同一个候选池，只做一轮成员认领与整组冲突筛选。这里禁止的是重复使用同一顶点，不是禁止不同事务之间存在图边。
5. **精确计算批次收益与容量。** 扫描真实受影响边，把不同事务之间的收益相互作用记入有序事件；每个分区对累计净重量与事件收益，选择当前次序中收益最大的可行前缀。虚拟中间前缀可以暂时不可行，实际只提交最终可行前缀。
6. **整体提交，再更新状态。** 一次提交被选事务的全部成员，更新真实cut、标签和分区重量；提交批次要求容量满足且cut严格降低。默认执行两批交换。

完整公式和具体边权例子见第8.8—8.9节。实现：[exchange.cuh](../src/refinement/exchange.cuh)与[complementary_moves.cuh](../src/refinement/complementary_moves.cuh)；调用位置：[incremental.cuh](../src/refinement/incremental.cuh) 第974行附近。

### 4.5 为什么这样组织适合GPU，开销又由什么控制

**把先后依赖转成同一任务内的联合判定。** 单向移动要等待反向移动释放的容量，现在通过净重量d一次计算。容量在事务内部抵消，再参与同批总净重量检查。一个合法交换批次不需要额外的“先移动至超载→再修复”过程；完整LP阶段仍保留修复。

**以分区对划分容量任务。** A—B与C—D不共享分区，因此不会竞争同一个分区的负载预算；跨配对的边在移动前后都连接不同分区，仍为切边。相同配对内部的边相互作用则用精确事件处理。这减少跨任务容量协调，而不是宣称匹配后一定比Jet拥有更多并行任务。

**以有界片段控制组合搜索。** 若短片段数为F，排序后，每个片段用O(log F)查找重量区间，最多检查四个伙伴，避免O(F²)的全体两两枚举。排序、真实邻边扫描和后续事件处理仍需计入。每轨迹最多8点、短前缀最多4项限制了候选状态规模，但顶点度数并不固定，所以不能把每个任务的时间写成常数。

**用精确边处理替代邻接排斥。** 不必仅为避免收益相互影响就排除所有相邻移动；warp协作扫描候选相关边，计算片段组合及事务之间的真实影响。一次统一冲突筛选、一次事件计划控制了批处理次数。当前前缀选择是不同分区对并行、每对按固定次序扫描，不能描述成所有候选上的全并行最优子集搜索。

**把较复杂搜索放在小层，把大层常规循环留在设备。** AR7仅在N≤65536的层执行，控制全点标记、候选排序和边扫描规模；AR6在N≥65536的层使用GPU条件图。两者分别处理有界交换搜索和大量常规迭代，不需要让大原图在每轮都支付交换搜索成本。互补机制能否减少达到同等cut所需的搜索时间，要结合质量和阶段计时；已经明确减少的主机往返与访问工作则对应AR3—AR6。

## 5. 跨阶段显存复用

多层 CSR、排序临时空间和细化缓冲具有不同生命周期。当前 arena 用少量底层 CUDA 块管理这些临时区间，采用 best-fit 分配、相邻空闲区间合并和默认流顺序复用。归还临时数组只修改主机元数据，最终同步后释放不再使用的底层块；其他流通过事件等待和出口 join 保证安全。

其直接效果是减少驱动分配/释放调用和池清理开销。所有分配、同步及释放仍在原生计时内，不通过移动计时边界获得加速。该机制是整条多层流水线的执行支撑。

源码：[scratch_pool.hpp](../include/detail/scratch_pool.hpp)。

## 6. 当前保留的改进清单：每项具体改变了什么

这里的“全部改进”指当前维护的生产路径，不把历史上撤回的尝试算进来。表中分清两种情况：**改变搜索对象、次序或预算的算法设计**，以及**计算相同对象时减少操作／数据搬运的执行优化**。实现分支根据结构或容量决定，不等于给每张图人工挑一套算法。

## 7. 完整粗化算法：从原图到最粗图

### 7.1 符号、输入输出与两种容量

- 当前层有 N 个顶点、M 条 CSR 邻接记录。无向图双向存储，M 通常是无向边数的两倍。
- 顶点重量为 w_v，边权为 w_uv；总重量 W=Σw_v，在层次之间守恒。
- 粗化映射 c(v) 表示顶点所属簇，簇重量 W_c=Σ_{v:c(v)=c}w_v。
- **簇容量 C_ℓ** 限制一个粗点代表多少原始重量；**分区容量 C=floor(1.03W/k)** 限制最终一个分区的重量，两者不同。
- 单层输出细点→粗点映射、粗点重量及粗 CSR；全部层的映射保存下来用于反粗化。

原图默认单位点重和边权，粗图携带聚合后的重量。当前顶点编号、设备CSR偏移为int32，点／边权为uint32；负载、cut与收益累计使用64位。磁盘CSR的64位字段在读取时检查可表示范围。窄类型优化依据范围证明，不是用近似权重换速度。

主流程是“每层可选一轮匹配种子 → 同一 CSR 上残余增长 → 收尾与编号压缩 → 一次粗 CSR 构造”。种子与增长共享簇状态，不会各跑一整套多层算法。

### 7.2 停止点数与渐进容量怎样计算

生产入口的目标因子为：

$$
\beta=\begin{cases}
\max(64,\lceil512/k\rceil),&k\le8,\\
\max(2,\lceil32/k\rceil),&k>8.
\end{cases}
$$

最多 24 层，点数降到 `max(32, βk)` 即停止。若单层聚合后没有减少点数，或者粗／细点数比大于 0.90，也停止，不为这次映射再构造粗 CSR。

k≥16 时，当前层因子为：

$$
\begin{aligned}
\beta_\ell &=\max\left(\beta,\min\left(\max(64,\lceil512/k\rceil),
\left\lceil\frac{N_\ell}{8k}\right\rceil\right)\right),\\[6pt]
C_\ell &=\max\left(\max_v w_v,\left\lceil\frac{W}{\beta_\ell k}\right\rceil\right).
\end{aligned}
$$

k≤8 使用固定 β_ℓ=β。细层因子大、容量紧；点数减少后逐渐允许更大的簇。它是结构层次的调度规则，不能说成单纯的数据类型或 kernel 优化。

源码：[partition_main.cu](../app/partition_main.cu) 参数设置；[coarsen.cu](../src/coarsen.cu) `coarsen_impl`、`aggregate_typed`；[coarsen.hpp](../include/coarsen.hpp)。

### 7.3 一轮匹配种子：何时做，怎样做

默认同时满足以下条件才做：N≥65536；没有 heavy-row 标记；整数平均度 M/N<8 或最大度界≤256；M/N<64；CSR 行有序且无重复邻居；边权为正。

这是**每层执行前判断**，不是跑完一种算法看效果再回退。符合条件时：

1. 每点选择重量允许的最强邻边，要求两个点总重量≤C_ℓ。
2. 相同边权用对称 hash 等固定规则打破平局；种子选择核函数跳过度数大于1024的源点。
3. 只提交互相选择的点对，较小 ID 为根；没成功的点仍各自成簇。
4. 更新簇重量，立即进入相同的残余增长流程。

低平均度时一线程一行，其他适用情形使用 warp。互选确保点对不重叠；这里只做一次，不对未匹配集合反复认领直至耗尽。

源码：[seed_matching.cuh](../src/coarsening/seed_matching.cuh)。

### 7.4 冻结 singleton mover 与稳定 receiver

只有仍是单点簇的根能成为迁移源。已有多点簇只接收，本轮不迁出；singleton 按 hash 分成源与接收者。

设当前簇数 n_c，参考目标 n_d=ceil(N/2)，本轮迁移概率为：

$$
f=\min\left(\frac12,\frac{\max(0,n_c-n_d)}{n_c}\right).
$$

hash 随层和轮次变化，但本轮角色冻结。目标必须是非 mover 的非空簇，并能按当前重量容纳整个源点。

这一步的作用可用一条链说明：如果允许 u→v、v→z 同时发生，提交就要处理 v 最终归谁、u 应指向哪个根。冻结角色后，u 的目标根本轮不会再迁移，直接写目标根即可。**稳定接收者是消除这一类提交依赖的原因。**

源码：[singleton_growth.cuh](../src/coarsening/singleton_growth.cuh) `residual_freeze_roles`。

### 7.5 精确亲和力与连接优势值：不是只看一条最重边

对每个活动源 v，计算：

$$
a(v,c)=\sum_{u:c(u)=c}w_{vu}.
$$

在角色和当前完整重量容量允许的不同接收簇中，找首选 a₁、次选 a₂；只有一个候选时次选为 0。正收益请求选择首选簇，优先级为：

$$
r(v)=a_1(v)-a_2(v).
$$

a₁ 是当前最好的连接，r是连接优势值，与第3节的Δa含义相同，衡量首选相对次选强多少。次选用于决定首选容量给谁；被拒绝的点留待后续轮次，不在本批立即改投次选。

精确聚合按结构选择实现：

| 情况 | 操作 |
| --- | --- |
| 未做种子、首轮、行有序唯一 | 每个邻点即不同簇，直接取首选／次选邻边，无须 hash 或 sort |
| 度≤8 | 8-lane 小组处理一行，按相同目标合并贡献 |
| 8<度≤256 | 每 warp 一行，用 512 槽共享 hash 聚合簇连接 |
| 度>256 | 只编码活动源的 `(v,c,w)` 记录，再排序归并；首轮超长 singleton 行另用一 CTA 分担 |

度数类别只在该层建立一次。源已合并后，在后续邻接扫描前被过滤。`second_affinity` 完成统计后复用为连接优势值（源码称 `regret`），省一份全点数组。

源码：[aggregation.cuh](../src/coarsening/aggregation.cuh)、[coarsen.cu](../src/coarsen.cu) `form_exact_proposals`。

### 7.5.1 单点能否加入单点：角色、重量和准入的完整公式

**可以。目标既可以是已有多点簇，也可以是一个没有被选为本轮迁移源的单点簇。** 残余增长中的单点加入单点，不要求双方互选：一个申请、一个接收即可；接收单点也可以同时接受多个源，只要完整重量前缀允许。它与前面种子阶段的两两互选是不同的步骤。

以下统一以当前层ℓ、增长轮t定义状态。当前图的点重w_v和边权ω_uv在本层增长期间不变；变化的是簇归属和簇重量。

**A．三种“重量”分别是什么。**

当前层顶点v的重量w_v表示它代表的原始顶点总重量。当前簇A的重量为：

$$
W_t(A)=\sum_{u\in A}w_u.
$$

顶点v到簇A的连接权重为：

$$
a_t(v,A)=\sum_{u\in A:\{v,u\}\in E_\ell}\omega_{vu}.
$$

前一个衡量容量，后一个衡量连接，二者不能混为一谈。连接没有除以簇重量或顶点重量。

**B．从哪些单点选迁移源。** 设当前簇集合为𝒞_t，簇数n_t，当前层原有点数N_ℓ。先计算抽取比例：

$$
f_t=\min\left(\frac12,\frac{\max(0,n_t-\lceil N_\ell/2\rceil)}{n_t}\right).
$$

用随层和轮次变化的32位hash H_ℓ,t，迁移源集合为：

$$
\mathcal D_t=\left\{v:\{v\}\in\mathcal C_t,\quad
H_{\ell,t}(v)<\lfloor 2^{32}f_t\rfloor\right\}.
$$

接收簇集合为：

$$
\mathcal R_t=\mathcal C_t\setminus\left\{\{v\}:v\in\mathcal D_t\right\}.
$$

因此多点簇必在接收集合中；未被抽中的单点也在其中。f_t≤1/2是hash抽取比例，不是每轮实际迁移源个数绝对不超过单点数量的一半。

**C．某个源v可以申请哪些簇。**

$$
\mathcal F_t(v)=\left\{A\in\mathcal R_t:
 a_t(v,A)>0,\quad W_t(A)+w_v\le C_\ell\right\}.
$$

三个条件缺一不可：接收角色、有正连接、按轮开始时的重量能放下整个v。若目标是单点A={u}，这些条件自动变为u不在𝒟_t、ω_vu>0、w_u+w_v≤C_ℓ，不需要u也选择v。

**D．选首选并计算连接优势值。**

$$
A_1(v)=\arg\max_{A\in\mathcal F_t(v)}a_t(v,A),\qquad
b_1(v)=a_t(v,A_1(v)).
$$

相同最大连接按固定hash／ID规则打破平局。次强值与优先级为：

$$
\begin{aligned}
b_2(v)&=\max\left(\{a_t(v,A):A\in\mathcal F_t(v),\ A\ne A_1(v)\}\cup\{0\}\right),\\
r_t(v)&=b_1(v)-b_2(v).
\end{aligned}
$$

两个不同目标的连接并列最大时，b₂=b₁，连接优势值为0；只有一个目标时b₂=0；没有目标则不申请。源是当前层singleton，因此在无自环图中，其原簇内部连接为0，单独加入首选的连接收益为b₁；排序使用的r却是b₁−b₂，二者不同。

**E．多个源同时申请目标A。** 令Q_t(A)为首选A的请求集合，按连接优势值降序排列为v₁,…,v_m；相同值用固定tie规则。剩余容量与前缀为：

$$
S_t(A)=C_\ell-W_t(A),\qquad
P_i=\sum_{j=1}^{i}w_{v_j}.
$$

接受条件精确为：

$$
v_i\text{ 被接收}\iff P_i\le S_t(A).
$$

这里不是仅检查w_v≤余量：所有申请都可能单独放得下，但一起放不下，所以要做累计前缀。若有充分界证明全部请求都放得下，接受结果相同，可省排序与前缀。

**F．一批完成后的状态。** 对每个接收簇A，令Acc_t(A)为它实际接受的源集合：

$$
\begin{aligned}
A'&=A\cup\operatorname{Acc}_t(A),\\
W_{t+1}(A')&=W_t(A)+\sum_{v\in\operatorname{Acc}_t(A)}w_v.
\end{aligned}
$$

被接收源的旧单点簇删除，被拒绝源保持单点。源与接收者不重叠，使这一批无需处理目标同时迁出的链式关系。总重量保持不变：

$$
\sum_{A'\in\mathcal C_{t+1}}W_{t+1}(A')
=\sum_{A\in\mathcal C_t}W_t(A)=W.
$$

**G．一个同时出现“加入多点簇”和“加入单点”的局部例子。** 假设当前层容量C_ℓ=4，接收者为A={a,b}（重量2）、B={c}（重量1）。本轮迁移源是u、v、z：

| 源 | 顶点重量 | 到A的连接 | 到B的连接 | 首选 | 连接优势值 |
| --- | ---: | ---: | ---: | --- | ---: |
| u | 1 | 9 | 8 | A | 1 |
| v | 2 | 8 | 2 | A | 6 |
| z | 1 | 1 | 5 | B | 4 |

这些连接均是边权之和，例如u–a为4、u–b为5，则到A为9；u–c为8，则到单点B为8。

A余量为2，先收连接优势值为6且重量为2的v；之后u的累计请求重量为3，超过余量，拒绝。B余量为3，接收重量为1的z。结果：

```text
A'={a,b,v}：重量4   ← 单点v加入已有多点簇
B'={c,z}：重量2     ← 单点z加入接收单点c
{u}：重量1         ← 容量竞争失败，保持单点
```

三个点组成A'但重量是4，因为v本身代表重量2；簇重量不是当前层成员个数。总重量2+1+1+2+1=7，合并后4+2+1=7。

**H．到下一层，边权怎样计算。** 本层所有增长与收尾完成后，粗点A的点重为Σ_{u∈A}w_u，两个不同粗点A、B之间的边权为：

$$
\omega'_{AB}=\sum_{\substack{u\in A,\ v\in B\\\{u,v\}\in E_\ell}}\omega_{uv},\qquad A\ne B.
$$

内部边不输出；无向边在这个公式中计一次，CSR分别存A→B与B→A两个相同权重，不把两方向加成双倍。增长期间只改簇归属，最后建粗图时才把这些权重写成下一层的顶点／边权。

### 7.6 完整重量前缀准入，以及一个具体例子

没有触发全接纳快路径时：稳定压缩有效请求；按目标簇升序、连接优势值降序、固定 tie 优先级排序；对每个接收簇做完整顶点重量的 inclusive scan。旧簇重量冻结为 W_c，请求 i 的前缀为 P_i，仅接受：

$$
P_i\le C_\ell-W_c.
$$

**例子：两个重量为 1 的点争抢同一个剩余槽。** A、B 簇容量均为 3，当前重量均为 2：

| 源 | 到 A 的连接 | 到 B 的连接 | 首选 | 连接优势值 |
| --- | ---: | ---: | --- | ---: |
| u | 8 | 7 | A | 1 |
| v | 7 | 1 | A | 6 |

A 只能收一个点。按首选连接强度会先选 u；按连接优势值会先选 v，因为 v 失去 A 的损失更大。u 留到后续轮次，可重新选择 B。这个例子解释容量优先级；没有假设本批立即完成 u→B，连接优势值也不是全局最优求解器。

**前缀不是装箱。** 若余量为 4，请求重量按顺序是 2、3、1，前缀为 2、5、6，则只收第一项；不会跳过第二项再装第三项。这个限定使准入可用排序、scan、并行判定实现。

源码：[capacity_admission.hpp](../include/detail/capacity_admission.hpp)、[coarsen.cu](../src/coarsen.cu) 准入循环。

### 7.7 什么情况下可以直接删掉排序与前缀

设接收簇重量上界为 B，最大度界为 D，singleton 最大重量为 m_max。正整数点重保证每簇最多含 B 个点，最多有 BD 条邻接记录，所以全部可能入簇请求的重量有保守界 BDm_max。

若

$$
B+BDm_{\max}\le C_\ell,
$$

全部有效请求必然装得下。代码保留角色与首选连接计算，但省略次强统计、排序、前缀和旧重量 gather。检查采用等价的除法形式避免溢出，提交后继续维护保守 B。

这里的体系结构逻辑非常具体：**容量语义证明没有竞争后，删除原本用于解决竞争的全局数据处理。** 不需要先超载再回滚，也没有放松容量。

### 7.8 四轮增长后的收尾

增长最多四轮；当簇数≤0.60N 时提前停止。

随后处理两类剩余结构：

- **孤立点打包：** 零度点按重量前缀分容量箱；完整重量区间落在同一箱中的点可合并，跨箱的点保留。因为没有关联边，不改变 cut。
- **残余 two-hop：** 若簇数仍>0.60N，为剩余 singleton 找偏好簇；共享偏好簇的点排序后相邻两项组成一对，满足合计重量容量并受 n_c−ceil(N/2) 合并预算限制才合并。

two-hop 是把**共享偏好对象的两个 singleton 彼此合并**，不是将它们都装入偏好簇，也不是把整个偏好组一次收成一个大簇。两点可以没有直接边。

最后将非空根压缩为连续编号，累加粗点重量，得到 fine_to_coarse。原 CSR 到这里仍未重建。

### 7.9 粗 CSR：局部路径与全局路径分别做什么

固定 map 后，内部边 c(u)=c(v) 删除，其余同一粗边权重相加。它与产生 map 的算法决策分开。

**短行路径：** 默认开启row-local；在已知记录界、正边权、细图N≥65536且最大度界≤512时统计原始粗行长度；整层所有原始粗行长度≤512才进入局部路径。流程为统计长度→扫描→细行scatter→warp内排序／归并→统计真实长度→扫描→输出。每行按32/64/128/256/512档处理；≤128与更长行分kernel。排序交换主要用寄存器和shuffle，scatter与输出仍访问显存。当前是整层选择，不是任意混合长行全局、短行局部。

**全局路径：** 编码粗边记录→radix sort→相同粗边精确reduce→生成CSR。若 `2*vertex_bits+weight_bits≤64`，可将源、目标、权重打包到一个64位记录；否则键值分开。排序只处理相关位。

特定 packed 大图路径（记录数≥2²⁰、平均度≥8、无heavy-row标记）在编码中做warp预合并，并在排序前压缩内部／无效记录；其他路径可以先排序哨兵再截去，不能统称所有路径都先删内部边。当前也没有无条件只排序无向边一半再镜像。

在固定映射下，这些路径都输出同一个精确加权CSR。性能区别在排序记录数量、记录字节数、片上复用与全局中间访问。

源码：[contraction_rows.cuh](../src/coarsening/contraction_rows.cuh)、[contraction_record.hpp](../include/detail/contraction_record.hpp)、[coarsen.cu](../src/coarsen.cu) `contract_typed`。

### 7.10 粗化伪代码

```text
Coarsen(G, k):
    检查并记录度数、行有序唯一、边权上界等元数据
    预留层次容器，工作区按需增长
    while N > max(32, β*k) and 层数 < 24:
        按 N、k 计算本层 β_level 和容量 C_level
        clusters = 符合结构条件 ? 一轮互选匹配种子 : 每点一个簇
        建立本层固定度数类别
        for round = 0..3:
            if cluster_count <= 0.60*N: break
            冻结 singleton movers 和稳定 receivers
            检查全部请求必然装得下的充分界
            计算活动源到可用接收簇的精确亲和力
            if 充分界成立:
                提交全部有效首选请求
            else:
                计算连接优势值，按目标及优先级排序

    return 层次、最粗图
```

## 8. 完整细化算法：LP、容量修复与互补交换怎样连起来

### 8.1 完整调用关系与初始状态

最粗图下载到CPU，对点权和边权分别做精确公约数归一化，经范围检查后调用一次 `METIS_PartGraphKway`，设置种子、零基编号、单重量约束、均等目标与失衡容限，再上传标签；不反复调用METIS寻找可修复初始化。这部分不作为我们的创新。源码：[initial_partition_metis.cu](../src/initial_partition_metis.cu)。随后：

```text
最粗图标签
  → 当前层必要时修复容量
  → LP 并行提案、优先级校正、移动、容量修复
  → 保存／恢复该层最好的可行状态
  → 若 N≤65536，执行两批容量互补交换
  → 投影到更细层
  → 判断本层是否需要细化
  → 重复直到原图
```

当前标签 p(v)，分区重量 L_p=Σ_{v:p(v)=p}w_v，容量 C。到分区的连接为：

$$
A(v,p)=\sum_{u:p(u)=p}w_{vu}.
$$

从 s 移至 t 的单点原始收益：

$$
g_0(v:s\to t)=A(v,t)-A(v,s).
$$

这是仅移动该点时的 cut 减少量。多个相邻点一起移动时，收益不能直接相加，后文分别解释 LP 的预测校正与交换的精确校正。

### 8.2 反粗化投影与哪些层实际细化

细图顶点直接继承其粗顶点标签：`fine_label[v]=coarse_label[map[v]]`。聚合时点重和边权精确相加，所以纯投影保持分区重量和 cut；生产路径直接复用，strict 验证模式另做独立重算。

最粗层先细化。之后进入中间层的条件为任一满足：

- 已到原图；
- 当前负载超容量；
- 当前点数≥上次成功细化点数的2倍。

其他层仅投影，连亲和力缓存都不建立。若粗层初始修复失败，不更新“上次成功细化点数”，后续更细层继续尝试。最终原图仍检查容量。

这是减少重复层次搜索的算法调度，不等价于“所有层运行相同工作但kernel更快”。

源码：[refine.cu](../src/refine.cu) `refine_hierarchy_device`、[uncoarsen.cu](../src/uncoarsen.cu)。

### 8.3 亲和力数据结构：到底存什么、怎样更新

| 表示 | 存储／查询 | 当前自动选择的主要条件 |
| --- | --- | --- |
| Dense | N×k 数组，A(v,p)直接索引 | 其他表示不合算时使用 |
| Sparse | 每行实际非零分区键及值，get按键查找，枚举直接读已有项 | Dense≥64MiB、估计空间至少省25%、无heavy rows，并满足稀疏程度／cut门槛 |
| OnDemand | 不建连接矩阵，查询时扫描CSR，只保存不变的行总边权等状态 | N≥65536、最大度≤16、已知cut≤N/500 |

Sparse 的槽位按 M 预留，不是按 Σq_v 精确分配；8位键和计数适用于当前 k≤128。亲和力计数能证明不超32位时使用32位，否则64位；分区重量、cut及有符号收益采用相应宽整数。

Sparse 选择还使用：旧布局估计节省至少一半、平均度≤8、cut≤M/40，或 k≥64 时的 cut 稀疏界。正整数边权给出 Σq_v≤N+2cut，因此可用 cut 判断连接稀疏性；这只是成本选择依据，不是实际分配字节数。

建表时，Sparse 的度≤16行用寄存器小数组聚合，不清零一个k长直方图。其他普通行用warp共享直方图，32位路径可先按相同分区做warp内合计，再原子累加。超长行另分担。

维护时，Dense 对受影响连接做增量更新；Sparse 标记受影响行并加入脏队列，提交后只重建这些行；OnDemand 从当前标签查询，不维护连接矩阵。**OnDemand 没有把每行自动变成一个持久小hash表，某些查询仍会重新扫描邻接。**

大层初始边界≤N/4时启用保守frontier：保存所有曾是边界及之后受影响的顶点，每点最多入队一次；变内部的点留在队列，提案时再过滤。这避免每轮全N扫描，又不会因直接删掉边界点而漏掉后续重新活跃的点。

源码：[affinity.cuh](../src/refinement/affinity.cuh)、[incremental.cuh](../src/refinement/incremental.cuh) 布局选择、`launch_affinity_build`、`initialize_affinity_frontier`。

### 8.4 LP 第一步：选目标，并允许有限的单点负收益探索

对本轮可参与点：

1. 上轮被LP移动的点有一轮锁，本轮清锁并跳过。
2. 若 A(v,p(v))等于该行总边权，非负边权说明它没有外部连接，直接跳过。
3. 枚举实际存在的外部分区连接。一般选连接最强目标；同值选较小分区ID。
4. 单位边权层允许的相对负收益阈值为0.25，加权边层为0.75。代码接受首选连接≥当前内部连接，或损失小于截断后的阈值乘内部连接。

保留有限负收益候选，是因为邻点一起移动后，该点的真实作用可能变好。此时尚未提交，接下来还要做邻域优先级校正。

**带权层的修复代价反馈。** 当 W>N 时，代码为分区维护修复价格 π_p，初始为0。修复过程中按源分区累计实际修复边变化的损失样本与移动重量，随后更新：

$$
\pi_p=\max(0,\mathrm{sample\_loss}_p/\mathrm{sample\_weight}_p).
$$

没有样本的分区保留原价。LP开始时负载可行，余量 s_p=C−L_p。移动重量w进入p的估计修复代价为：

$$
R(p,w)=\pi_p\max(0,w-s_p).
$$

该层选目标改为最大化 `A(v,p)−R(p,w_v)`。例如余量0、价格3、目标连接10，重量2的点得分4；另一个余量足够、连接7的分区得分7，因而选后者。它是在连接质量和预计修复代价之间做选择，不是预测最终精确cut的公式。

这部分改变LP的决策，必须写入当前完整算法，不能只说“沿用普通LP然后做交换”。初始容量修复不用于直接初始化价格，价格由后续LP触发的修复更新。

源码：`incremental_lp_proposal`、`estimated_repair_cost`、`publish_repair_prices`，均在 [incremental.cuh](../src/refinement/incremental.cuh)。

### 8.5 LP 第二步：afterburner 优先级校正

每个候选有原始收益 g_v 和目标 t_v。邻点u优先级高于v的规则为：g_u>g_v，或收益相同且u的ID更小。计算v时，假设高优先级候选邻点采用目标标签，其余邻点维持旧标签。

设v原分区为s_v，校正收益为：

$$
\widetilde g_v=g_v+\sum_{u\succ v}w_{vu}
\left([t_u=t_v]-[t_u=s_v]-[p(u)=t_v]+[p(u)=s_v]\right).
$$

常规路径保留非负校正收益。带价格的路径再加 `R(s_v,w_v)−R(t_v,w_v)` 后判断。

这一步让邻接候选可以共同推进，不像独立集合那样先禁止相邻移动。它是按优先级假设的预测，不是任意并行候选集合的严格联合收益；因此后续仍用真实边计算cut，并保留最佳可行检查点。

普通行用warp校正，度≥4096的行按32个CTA分担完整邻接工作。被接受点用warp ballot／合计预留方式压缩为移动列表。

源码：`incremental_priority_filter`、`incremental_heavy_priority`、`incremental_finish_heavy_priority`。

### 8.6 LP 第三步：真实边更新、容量修复、最佳状态

一次批量移动按以下顺序执行：

1. 通过旧标签、目标和移动标志，对受影响边计算移动前后是否切边，按唯一归属计数，获得精确cut变化。
2. 在同一遍邻接工作中维护Dense连接或标记Sparse脏行，而不是为cut和cache各扫一次。
3. 提交标签和完整顶点重量变化；重建Sparse脏行。
4. 若超容量，执行下一节的容量修复。
5. 如果修复可行且cut更低，保存该层最好标签和重量；否则不覆盖最好状态。

最多32轮，默认连续3轮未得到足够进展停止；代码在改进超过原best的0.1%时重置stale，任何更低cut仍可保存检查点；连续两轮空移动也停止。LP或修复不必每一步都使cut下降，层结束恢复最佳可行状态。

N≥65536时，LP循环、嵌套修复和条件检查点写入CUDA条件图。设备决定是否再循环，主机在调用边界读取结果；小层用主机控制相同流程。图的构建、实例化、销毁仍计入耗时，且条件图仍由多个kernel组成。

源码：[lp_graph.cuh](../src/refinement/lp_graph.cuh)、[incremental.cuh](../src/refinement/incremental.cuh) `run_incremental_refinement_typed`。

### 8.7 容量修复：整点从超载分区移到哪里

**第一步：确定donor。** 只处理源分区 L_s>C 的点，包括内部点。N≥65536时每轮扫描全N并压缩donor列表；小层直接在提案扫描中按源负载过滤。冻结本轮源负载和接收者余量。内部点也可能需要迁移才能恢复平衡。

**第二步：形成初始目标。** 候选目标必须能容纳整个w_v，按连接降序、余量降序、分区ID升序选。Sparse枚举已有键；Dense直接查矩阵。若内部连接等于行总权重，知道所有外部连接为0，省去连接查询。

没有合适的正连接目标时，保留按可用余量加权的hash后备路由。若该点能放入所有有余量的接收者，可使用本轮余量CDF二分；否则扫描实际能放下它的分区。初始后备不是简单的“总选最大余量”。

**第三步：源侧按超载量分配申请资格。** 设超载 e_s=L_s−C，原始迁移收益g，以 `g/min(w_v,e_s)` 衡量每单位有效卸载的代价。使用50个收益／损失桶，每桶16个hash section，共800槽／分区。正收益优先，零收益其次，负收益按对数损失分档。

桶与section做重量前缀，顶点记录在桶内的重量排名。若其前缀起点小于e_s，就可申请迁出。这里比较起点，所以最后一个整点可让卸载重量超过e_s，而不是拆开顶点。

按 `min(w_v,e_s)` 归一化损失的思想在Jet强修复中已有。我们的对应执行改动是目标访问、桶前缀、接收票据与设备循环的组织，不能把归一化本身列作新增贡献。

**第四步：接收者完整重量预约。** 同warp请求同一目标的点用 `match_any` 合并，先算各点在组内的重量前缀，由组长做一次 `atomicAdd` 申请整段票号。只有整个点的票号区间落在冻结余量内才接受。

失败点最多尝试k个不同目标，用位集记住已试目标。retry依据动态剩余余量重新选目标，优先连接再余量；此阶段仍可能扫描全部k。失败的虚拟票号本轮不回收，下一轮重新计算实际余量。

**第五步：更新并继续。** 压缩成功移动、维护精确cut/cache/labels/loads，然后检查容量。可行即停；没有移动或达到2k+4轮也停。粗层初始修复失败时允许投影到更细层，再用更小的点尝试；最终原图必须满足容量。

这里的性能来源是稀疏枚举、无外部连接证明、源侧桶扫描、warp合并原子，以及设备端循环。它并没有取消完整顶点约束。

源码：[rebalance_select.cuh](../src/refinement/rebalance_select.cuh)、[rebalance_graph.cuh](../src/refinement/rebalance_graph.cuh)、[incremental.cuh](../src/refinement/incremental.cuh) 修复提案与边更新。

### 8.8 容量互补交换：解决单独不能动、合起来能动的问题

恢复最好可行LP状态后，在N≤65536的层执行默认两批交换。若恢复了旧标签，先重建与它一致的亲和力。

对分区A、B，S从A到B，T从B到A，净重量为：

$$
d=w(S)-w(T).
$$

移动后 `L_A'=L_A−d`、`L_B'=L_B+d`，所以严格可行区间是：

$$
L_A-C\le d\le C-L_B.
$$

当两边都满时，区间为[0,0]；单个正重量片段不能移动，但两个方向重量相抵就可能可行。我们的搜索因此保留暂时单独不可行的片段，等组合时再判断完整容量。

联合收益也可以直接从单点收益展开。用w(E[S])表示S内边权之和、w(S,T)表示两集合之间边权之和，无向边均计一次，则：

$$
\begin{aligned}
G(S,T) &=\sum_{v\in S}g_0(v:A\to B)+\sum_{v\in T}g_0(v:B\to A)\\
&\quad+2w(E[S])+2w(E[T])-2w(S,T).
\end{aligned}
$$

同侧一起移动的内部边需要加回两次；异侧交换后仍为切边的连接需要减去两次。生长、片段组合与最终事件计算分别在自己的阶段维护这些真实相互作用。

#### 8.8.1 商图配对：限定本批耦合范围

构造商图Q_AB，值为两个分区之间的总连接权重。对未匹配分区按

$$
Q_{AB}/(1+\mathrm{visits}_{AB})^2
$$

选择伙伴，互选后配对，继续寻找剩余配对；同一批分区不重复参与。访问惩罚鼓励探索其他伙伴，但不保证下一批一定换伙伴。商图在当前层交换开始时建一次，默认两批之间不重建。

这使容量约束局限于每个分区对。属于不同配对的顶点移动前后始终位于不同分区，连接它们的边始终是切边；只有同一配对内需要计算相互作用。

#### 8.8.2 种子与双向生长：一条轨迹具体怎样产生

每分区种子槽数为 `min(128,max(32,4096/k))`。只连接当前伙伴的边界点参与，按hash分桶，每桶保留最小编码，不是按单点gain只取正收益。每种子跑两条策略，一warp一轨迹，总轨迹槽数为 `2*k*seed_width`，最多8192。

从正向根开始，维护成员、两侧计数、精确gain与净重量net。每侧最多4点，总计最多8点。允许负收益中间状态。扩展规则是：

1. 同侧从已有成员的邻居扩展；反向尚为空时，也可从伙伴种子开始反向侧。
2. 每个成员只提名CSR前128个邻居；新加入点度数≤1024；根种子不受这个新点限制。
3. 若net高于可行上界，只允许增加反向重量；低于下界，只允许增加正向重量。
4. 便宜提名分数使用单点收益和当前提名边的修正；策略0在不可行时先减容量缺口，策略1先看收益。状态已可行时，两策略可能相同。
5. 选中下一点后，再扫描其完整CSR，对所有已有成员计算真实边际：与同侧成员连接加2w，与异侧成员连接减2w。更新精确gain与net。

提名预算限制搜索范围；**被保留下来的片段gain使用完整边计算**。当前不是top-4精确重选或beam search，便宜提名后也不因真实分数下降而回退重选。

#### 8.8.3 同一轨迹输出什么：长可行状态与短片段档案

每条轨迹同时输出两类结果：

- 生长过程中精确gain最大的一个正收益可行状态，可最多8点。
- 前4个成员规模对应的正收益前缀，各存一项，**即使单独容量不可行也存**。最多4项，不是任意大小的Pareto前沿。

短片段以规范化分区对、净重量、gain、大小、排序成员ID组织。完全相同的成员集合和目标去重；同净重量但形状不同的片段仍保留，因为后续冲突、边相互作用不同。

#### 8.8.4 互补组合：先看净重量区间，再精确算收益

同一分区对的片段按净重量排序。片段i净重d_i，对它的互补片段j要求：

$$
\mathrm{lo}-d_i\le d_j\le\mathrm{hi}-d_i.
$$

二分找到这个区间，最多取4个分散代表检查。要求成员不重叠，合计≤8点；精确修正跨片段边，保留最好的正收益组合。合法短片段本身、长可行状态和组合进入**同一个候选池**。

对不重叠的片段x、y，精确组合收益为：

$$
\begin{aligned}
G(x\cup y) &=G(x)+G(y)\\
&\quad+2\!\sum_{\substack{u\in x,v\in y\\p(u)=p(v)}}w_{uv}
-2\!\sum_{\substack{u\in x,v\in y\\p(u)\ne p(v)}}w_{uv}.
\end{aligned}
$$

同侧跨片段边在两点一起移动时仍内部，需加回；异侧两点交换后仍切边，需减去单独移动时重复计入的收益。组合被当成不可拆事务，可以由不连通片段组成。

#### 8.8.5 冲突、精确事件与前缀提交

1. 候选按规范化分区对、gain降序、ID排序。
2. 对每个成员 `atomicMin` 认领排序位置；没有拥有全部成员的事务整组删除。当前只有一次claim／resolve，不做多轮冲突恢复。
3. 对幸存事务建立顶点owner和目标标签。
4. 遍历受影响边，生成该排序下的精确gain事件：同一事务两端一起变；不同事务则分别在先执行者与后执行者位置记录边状态变化。不同匹配对之间的边不产生gain变化。
5. 每个分区对扫描自己的事务段，累计事件gain与净重量，选择**这个固定次序中**收益最大的容量可行前缀。
6. 虚拟扫描的中间前缀可以暂时超容量，但只提交最终可行前缀；事务不能拆开。
7. 一次提交所选事务，更新真实cut与负载，检查容量满足且cut严格降低。

“精确”指真实边相互作用、最终容量和所选前缀的收益；不是求所有候选的任意最优子集。一次冲突筛选与一次事件计划控制了每批执行量。

**事件如何在GPU上计算。** 一个warp负责一个事务i，32个lane协同访问成员的邻接行。原实现对每条有效边都向本事务的`events[i]`原子累加；跨事务边另向另一事务的位置累加。10月22日改为每个lane先累计本事务的贡献，再用五步shuffle归约，最终至多一次原子写回`events[i]`。另一事务的贡献仍直接写原位置，因此事件顺序、前缀收益和接受结果保持相同。最终写回仍须是原子操作，因为其他warp也可能贡献到i。正负贡献用无符号64位模加法累计，与原原子加的表示一致；空事务按整个warp退出。

设经过边去重及过滤后实际处理E条边，其中X条连接不同事务，T个事务的本地贡献和非零。原事件生成执行E+X次全局原子加，新实现执行X+T次；减少的是本事务贡献的重复写回，邻接读取和远端事件数量不变。它增加每个活动warp五步shuffle和局部累加；实际时间收益需要GPU计时。这是精确事件计算的执行优化，与容量互补候选机制属于不同层面的改动。

例如权重为w的边两端原来分属A、B，分别由先后两个事务交换方向：第一端移动后该边变内部，先事务位置记+w；第二端移动后又变切边，后事务位置记−w，最终合计0。若只把各事务独立收益相加，会将这条边算成2w收益。事件方法精确记录的是这段状态变化。

源码：[exchange.cuh](../src/refinement/exchange.cuh) `joint_quotient/match/seeds/grow/claim/resolve/events/prefix/accept`；[complementary_moves.cuh](../src/refinement/complementary_moves.cuh) `joint_combine`；[incremental.cuh](../src/refinement/incremental.cuh) 交换调用链。

### 8.9 一个完整数值例子：为什么两个不能单独动的片段可以降低cut

用五个加权点演示。容量C=10：

| 分区 | 点及重量 | 总重量 |
| --- | --- | ---: |
| A | a:8，u₁:1，u₂:1 | 10 |
| B | b:8，v:2 | 10 |

无向边为：u₁–a:1、u₁–b:4、u₂–a:1、u₂–b:3、v–a:4、v–b:1、u₁–u₂:2、u₁–v:1。初始切边为4+3+4+1=12。

选正向片段S={u₁,u₂}、反向片段T={v}：

- 单点g₀(u₁)=(4+1)−(1+2)=2，g₀(u₂)=3−(1+2)=0。
- S共同移动时，u₁–u₂保持内部，故G(S)=2+0+2×2=6，净重+2；单独移动会使B重量变12，不可行。
- G(T)=(4+1)−1=4，净重−2；单独移动使A重量变12，也不可行。
- 合并后净重0，两边仍各10。跨片段边u₁–v交换后仍切边，需修正−2×1。
- 最终收益G(S,T)=6+4−2=8，cut从12降到4。

这体现当前机制的关键：**不是降低平衡要求，而是延后对片段的单独可行性过滤，按容量互补组合成一个严格可行事务。** 数值例子用于解释算法，不是某数据集上的测量。

### 8.11 为什么这条细化主线有机会同时改善质量与时间

要分开看两条因果链：

- **质量链：** 单点／单向容量过滤会丢掉互相腾挪才可行的移动 → 保留带净重量的短片段 → 有界组合与真实边校正 → 提交可行且正收益的事务。
- **执行链：** 全矩阵维护、重复目标查询、无变化内部点扫描、每轮主机判定会占用时间 → 选连接表示、缩小活动域、融合边维护、warp合并预约、设备条件循环 → 相同基础细化任务的管理和访问成本下降。

交换本身会增加搜索，不能把加入交换自动解释成每个配置都更快。当前完整系统的速度来自搜索预算、层次调度与执行优化共同作用，质量来自实际接受的移动与检查点；各项已有证据见下一节。

**粗化主线不是“把HEM和LP混用”，而是如何组织容量竞争与增长；细化主线也不是“增加一种LP打分”，而是让带净重量的片段活到组合阶段，再整体提交。** 匹配种子、常规LP、修复和存储布局分别服务于这两个方法所在的完整流水线。

修复价格反馈属于现有细化中的决策补充，文档已完整展开；它不需要与容量互补交换并列成第三种主算法。短行CSR、稀疏查询、条件图与arena则分别对应建图、访问、控制和生命周期成本。

### 10.2 为什么更快：用具体操作量表达，避免只讲GPU并行度

**粗化增长的工作单位。** 一轮保留角色／状态等O(N)处理，但主要邻接工作只覆盖活动源，其量约为Σ_active d_v；高度源还会产生需要排序的边记录，竞争接收者需要排序P个请求并做重量scan。成功源退出下一轮的Σ_active d_v；全接纳证明成立时，P条请求的排序／scan可直接消失。粗化仍有主机读取簇数等操作，没有把整条粗化循环搬成GPU条件图。

**缓存和目标访问的工作单位。** G-kway一条需要更新的行涉及q_v个目标时，重复gain查询约读取q_v*d_v条邻接。例如d_v=256、q_v=32，仅重复扫描部分就约8192条记录；一次聚合读取256条原记录，再访问聚合结果。Acc-GPart的Dense增量维护和Sparse脏行重建减少这种重复，但要付出缓存构造／更新成本。Jet已有缓存，对Jet的区别应转向表示选择、活动域和循环控制，不能复用“消除逐目标重扫”解释所有基线。

**容量修复的工作单位。** Sparse初始目标选择原本对k个目标逐个查稀疏行，最坏O(kq_v)；枚举实际键变成O(q_v)，零连接后备另计。warp内若h个点请求同一接收者，将h次请求计数原子改为一次总重量原子及组内前缀；同组所有点仍各自按完整重量判断。

**控制的工作单位。** 将“LP→检测超载→修复循环→检查点→下一轮”放在设备条件图，减少每轮为主机判断而返回标量与等待的次数。依赖没有消失，而是由设备执行图承接。主机仍参与层次切换、METIS和小层控制。

**数据与生命周期的工作单位。** 短行CSR使局部排序中间交换使用寄存器／shuffle；位宽打包减少每条中间记录的字节；arena减少底层分配API次数。这些可以分别用记录数／字节、阶段时间、API调用与时间检查，无须把“占用率高”当成加速结论。

### 10.4 贡献组织与性能证据的连接


最适合继续展开的统一论点是：**通过重组图划分中受容量与邻接依赖约束的工作，形成可批量推进的 GPU 计算，同时控制全局数据维护与主机协调。**

粗化贡献可以围绕“稳定接收簇聚合”展开：冻结角色消除同轮迁移链，多点准入与有界增长控制重复匹配和残余搜索，连接优势值分配有限簇容量，全接纳证明与短行归并降低执行成本。算法步骤和对应瓶颈见第3节三列流程。

细化贡献可以围绕“容量互补的批量移动”展开：净重量保留跨方向依赖，分区对匹配限定容量耦合范围，有界组合和真实边修正产生可提交事务，活动集合与设备端循环支撑整体执行。

第三项仍可以是完整划分器及实验验证。体系结构论述不要求另造第三种算法；访存、调度和显存管理应与前两项机制及相应阶段的证据对应。

在后续对比中，最有解释力的量是：每层活动边数/匹配或传播轮数、每批实际移动数/扫描边数、主机同步次数与 GPU 空隙、CSR 中间记录量、分配 API 调用与时间。它们能把“为什么快”落实到工作量与执行成本，而不是用较高 occupancy 或较多线程作为提速的替代解释。

### 10.5 论文中如何连接挑战与贡献

引言中用两项挑战对应两个机制即可。挑战段说明依赖带来的执行成本，方法段说明我们如何改变任务组织；短行CSR、warp归约、缓存和arena放到方法的GPU实现部分展开。

**粗化挑战。** 匹配竞争与合并依赖使GPU需要多轮协调才能确定聚合结果。重复邻接搜索、组标识传播和逐渐缩小的活动集合增加了执行开销；扩大聚合批量又需要在有限簇容量下保留强连接结构。

**对应贡献。** 我们提出稳定接收簇聚合：每轮固定接收簇，允许多个单点直接加入，省去同轮合并链的解析；按连接优势和重量前缀批量分配容量，并限制残余增长轮数，控制重复处理。

**细化挑战。** 顶点移动之间的收益耦合与容量依赖限制了并行批量。逐点过滤会遗漏互补移动，而并行移动后的负载修复和反复状态维护又增加了执行成本。重复邻接访问与主机控制进一步降低了迭代效率。

**对应贡献。** 我们提出容量互补交换，将相互释放容量的短移动组合后整体选择和提交。通过分区对划分容量任务，以精确边收益处理相邻移动的相互作用，并用有界候选搜索控制组合开销。设备端迭代、连接复用和局部归约进一步降低执行成本。

粗化的执行优势落在“归属直接确定、容量批量分配、残余处理有界”；细化落在“容量依赖在交换内处理、边交互精确计算、常规迭代与数据维护减少往返”。互补交换增加了可表达的移动组合，但并不由此自动推出细化轮数更少；相应时间结论使用第9节对应版本的证据。
